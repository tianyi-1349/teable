# Published App Runtime Requirements

## Overview

This specification defines the cross-device Published App Runtime for Teable. The goal is to align Teable's app-mode publishing experience with a complete business application runtime: a published base can be opened as a stable, navigable, responsive application across desktop web, tablet web, mobile web, embed mode, and installable PWA.

WeChat Mini Program support is intentionally out of scope for this implementation phase. The architecture must keep headless manifest, navigation model, and renderer adapter boundaries so a Mini Program renderer can be added later without rewriting the published app model.

## Scope

### In Scope

- Web Published App Runtime for authenticated and shared/published contexts.
- App node route closure for logged-in and share routes.
- Cross-device app shell for desktop, tablet, mobile, embed, and PWA standalone contexts.
- Published app manifest derived from base, share, publish info, and base nodes.
- Unified navigation model based on published nodes and runtime `defaultNodeId`.
- Resource renderer abstraction for Table, Dashboard, Workflow, App, and unsupported resources.
- Mobile-friendly and cross-device behavior for Dashboard, Chart, Table, Form, and shared views.
- Cross-device preview and validation in the publish dialog.
- Security, permission, iframe, performance, compatibility, and rollback controls.

### Out of Scope

- Native iOS or Android apps.
- WeChat Mini Program frontend implementation.
- Mini Program login, sharing, chart renderer, form renderer, or attachment renderer.
- Full low-code app builder or AI app generator.
- New page DSL for custom app building.
- Offline editing and conflict resolution.

## Definitions

- **Published App Runtime**: The runtime shell, context, navigation, and resource renderer used to open a published base as an application.
- **Published App Manifest**: A headless, structured description of the published app, including app identity, nodes, default node, permissions, and supported runtime targets.
- **Published Navigation Model**: A device-neutral representation of app pages derived from base nodes and publish info.
- **Shell**: A responsive layout wrapper selected by device/runtime target, such as desktop, tablet, mobile, embed, or PWA standalone.
- **Resource Renderer**: A renderer that displays a specific resource type, such as Table, Dashboard, Workflow, or App.

## Requirements

### R1: App Node Route Closure

The system shall render `BaseNodeResourceType.App` nodes in authenticated base routes and shared/published base routes.

Acceptance Criteria:

- `/base/{baseId}/app/{appId}` opens a valid App node runtime page.
- `/share/{shareId}/base/{baseId}/app/{appId}` opens a valid shared App node runtime page.
- App routes do not return placeholder content or `notFound` when the App node exists and is accessible.
- Missing or unsupported App runtime content renders a clear unavailable state instead of a blank page.
- Existing Table, Dashboard, and Workflow routes keep their current behavior.

### R2: Unified Resource Resolution

The system shall resolve Table, Dashboard, Workflow, and App resources through one consistent route and resource resolution path.

Acceptance Criteria:

- Logged-in and shared routes use the same renderable resource type rules.
- App URLs generated by base node helpers are accepted by route dispatch.
- Unsupported resources return an explicit unsupported state.
- Existing legacy table URL redirects continue to work.

### R3: Published App Manifest

The system shall derive a device-neutral published app manifest from base data, share data, base nodes, and publish info.

Acceptance Criteria:

- The manifest includes app title, icon when available, base ID, share ID when applicable, nodes, default node, permissions, and runtime targets.
- The manifest does not depend on DOM, Next.js router objects, iframe APIs, or React component instances.
- The manifest can represent single-node share and multi-node published app modes.
- The manifest preserves future Mini Program renderer compatibility without implementing Mini Program behavior.

### R4: Published App Context

The system shall expose runtime state through a Published App Context.

Acceptance Criteria:

- Current node, default node, node list, permissions, share state, read-only state, and runtime target are available from one context.
- Navigation components and resource renderers use the same context.
- Single-node share does not display multi-page navigation unless the manifest represents a multi-node app.

### R5: Cross-Device Shell

The system shall render published apps through responsive shells for desktop, tablet, mobile, embed, and PWA standalone contexts.

Acceptance Criteria:

- Desktop web can use side navigation or split layout.
- Tablet web can use an adaptive drawer/split layout.
- Mobile web uses an application-style header, bottom navigation, and page drawer instead of an editor-style tree sidebar.
- Embed mode uses minimal chrome.
- PWA standalone mode respects safe-area insets and app-like navigation.
- Device shell changes do not change resource semantics or current node identity.

### R6: Published Navigation Model

The system shall derive navigation from published nodes and runtime `defaultNodeId`.

Acceptance Criteria:

- `publishInfo.nodes` controls published app page visibility.
- The runtime manifest exposes `defaultNodeId` as the canonical default app entry.
- Source publish configuration may still store this selection as `defaultActiveNodeId`, but runtime contracts and runtime consumers use `defaultNodeId`.
- If the default node is invalid, the system falls back to the first renderable published node.
- Folder nodes are rendered as navigation groups, not resource pages.
- Direct access to resources outside the published node set is denied with a clear state.

### R7: Resource Renderer Layer

The system shall render published resources through a resource renderer abstraction.

Acceptance Criteria:

- Table, Dashboard, Workflow, and App resources are routed through the renderer layer.
- Unsupported resources render a consistent unsupported state.
- Resource failures are isolated by error boundaries and do not crash the full app shell.
- Shared and authenticated contexts reuse the same resource renderer rules where possible.

### R8: Dashboard and Chart Cross-Device Behavior

The system shall make Dashboard and Chart resources usable in published app contexts across supported devices.

Acceptance Criteria:

- Published Dashboard disables editing interactions such as drag and resize.
- Mobile Dashboard avoids page-level horizontal overflow.
- Chart interactions support touch-first use, not hover-only behavior.
- Plugin cards can fail independently without crashing the Dashboard page.
- Dashboard edit mode behavior is not regressed.

### R9: Table, Form, and View Cross-Device Behavior

The system shall make shared Table, Form, and View resources usable in published app contexts across supported devices.

Acceptance Criteria:

- Mobile table experiences provide a card/list or other touch-friendly fallback when grid is not suitable.
- Records can be opened in a mobile-friendly detail view.
- Search, filter, and sort controls are accessible through compact responsive controls.
- Forms are usable on mobile devices, including keyboard and validation behavior.
- `allowEdit=false` hides editing affordances in the client, and backend permission checks remain authoritative.

### R10: Publish Preview and Validation

The system shall detect common published app issues before publishing.

Acceptance Criteria:

- The publish dialog offers cross-device preview targets for desktop, tablet, mobile, embed, and PWA.
- Validation reports errors, warnings, and informational notes.
- Publishing is blocked for fatal configuration errors, such as no published nodes or invalid default node.
- App nodes without usable runtime content are reported.
- Mini Program compatibility is reserved as a future target and does not block current publishing.

### R11: PWA and Installable Web App Support

The system should support installable web app behavior for published apps.

Acceptance Criteria:

- Published apps can expose app title, icon, start URL, theme color, and standalone display metadata where feasible.
- Standalone mobile mode handles safe-area insets.
- Refreshing or reopening preserves the default node or current deep link.
- Offline or weak-network states show clear retryable errors.

### R12: Security and Permission Boundaries

The system shall preserve share permissions and prevent credential leakage.

Acceptance Criteria:

- Shared App resources inherit base share permissions.
- External App URLs do not receive internal JWTs, share passwords, or private credentials.
- iframe usage applies a conservative sandbox and clear fallback behavior.
- `postMessage` integration is not enabled in this phase.
- Backend permission checks remain authoritative for write operations.

### R13: Performance and Stability

The system shall keep published app runtime stable and responsive on mobile devices.

Acceptance Criteria:

- Initial app load only fetches the current resource's heavy data.
- Navigation metadata is lightweight.
- Dashboard plugins and external App frames are lazy loaded where possible.
- Table data is paginated or virtualized in mobile-heavy scenarios.
- A single resource or plugin failure does not crash the shell.

### R14: Backward Compatibility and Rollback

The system shall preserve existing published and shared URLs.

Acceptance Criteria:

- Existing share base, table, dashboard, and workflow URLs continue to work.
- New App routes are additive.
- New shell behavior can be guarded or rolled back without removing App route closure.
- Existing publish permalink behavior is preserved.
